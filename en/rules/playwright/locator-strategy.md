# Locator Strategy

Complete six-level priority (P0 → P5) and selection flow → [locator-replacer skill](../../skills/locator-replacer/SKILL.md).

---

## Absolutely Forbidden

- **Hash class names**: `sc-bdVaJa`, `css-1a2b3c`, `._module_xxx` (generated by build tools, changes every build)
- **Absolute XPath**: `/html/body/div[1]/div[2]/...` (breaks on any page change)
- **Pure numeric index**: `div[3]` (unless a list genuinely requires the Nth item)

> Detailed hash class name identification rules (by build tool) → [locator-replacer skill](../../skills/locator-replacer/SKILL.md) "Hash Class Name Identification Rules"

---

## State-Class Selector Must Be Anchored with Text

`.active` / `aria-selected` and similar state classes match "whoever is currently in that state"; they drift after tab switching.

❌ Anti-pattern:

```python
OVERVIEW_ACTIVE = "css=ul.tab-bar li.tab.active"   # still matches after switching to another tab
```

✅ Best practice:

```python
OVERVIEW_ACTIVE = "css=ul.tab-bar li.tab.active >> text=Start Tab Name"   # .active + specific text
```

## Annotation Convention

Annotate `# P0`~`# P5` at the end of each locator line. Full level definitions → [locator-replacer skill](../../skills/locator-replacer/SKILL.md)

## ARIA Role Must Be Verified First

Do not guess the role from the UI appearance. Many frameworks use `<div>` / `<li>` + CSS to simulate components without a `role` attribute.

❌ Anti-pattern:

```python
TAB = "role=tab[name='Details']"    # actually a <li> without role → timeout
```

✅ Best practice:

```python
# Verify DOM first: <li class="active">Details</li> (no role)
TAB = "css=.tab-container li:has-text('Details')"    # P3+P1
```

---

## `>>` Chained Locator: Fails When Text Is Directly Inside Parent Element

When text is directly the element's textContent (e.g. `<li>Details</li>`), `css=X >> text=Y` may find no match.

❌ Anti-pattern:

```python
TAB = "css=.tab-container li >> text=Details"    # <li> has no child elements → timeout
```

✅ Best practice:

```python
TAB = "css=.tab-container li:has-text('Details')"    # :has-text() matches element's own text
TAB = "css=.tab-container li:text-is('Details')"     # :text-is() exact match
```

---

## `text=X` Is Substring Match — Use Exact Match When There Are Containing Relationships

`text=Add` will match both "Add" and "Batch Add".

❌ Anti-pattern:

```python
ADD_BTN = "text=Add"        # .first hits "Batch Add"
GENERATE_BTN = "text=Generate"   # hits "Generate" substring in description paragraph
```

✅ Best practice:

```python
ADD_BTN = 'text="Add"'       # with quotes = exact match
# or use CSS scope to limit
ADD_BTN = "css=.list-card >> text=Add"
```

### High-Risk Variant: Substring Match Hits Toggle Button Causing Cascade Failure

When the operation button's text is a substring of a toggle button (e.g. "Filter" vs. "Collapse Filter"), the substring match may preferentially hit the toggle button, triggering a **side effect** (e.g. collapsing the panel), causing the target button to disappear and all subsequent operations to execute in the wrong state.

This type of bug is particularly insidious: the test will not report "element not found" — instead it executes subsequent operations on unfiltered full data (e.g. deletes the wrong data), and assertions may happen to pass.

❌ Anti-pattern:

```python
# text=Filter substring match, .first hits "Collapse Filter" → panel collapses → real "Filter" button disappears
# → search not executed → subsequent operations on wrong data in the full list
FILTER_BTN = "css=.list-content >> text=Filter"
```

✅ Best practice:

```python
FILTER_BTN = 'css=.list-content >> text="Filter"'   # exact match, doesn't hit "Collapse Filter"
```

**Diagnostic signal**: After the operation, expected state doesn't change (panel collapsed, search not executed, list not filtered), but subsequent steps don't error → check if a same-name substring toggle button was accidentally clicked.
